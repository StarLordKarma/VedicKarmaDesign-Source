# Локальная песочница карточной оплаты и ручного возврата

Рабочий сайт и GitHub не обновлялись. Вызовы live API RiskPay отключены: его платёжный маршрут, seller No-KYC и условия возвратов требуют подтверждения. Все карточные операции и переводы в этом контуре — mock. Не вводите реквизиты настоящих карт.

## Что собрано

Основная страница `reading-core` сохраняет существующий дизайн и четыре языка. В форме заказа добавлены варианты: существующая криптооплата, Visa/Mastercard, Apple Pay и Google Pay. Выбор Apple/Google сохраняет предпочтение; фактическая доступность зависит от hosted checkout. Карточный блок появляется только при проверенной локальной sandbox-конфигурации. Для production режимов он скрыт, а запросы карточного checkout отвергаются сервером до создания заказа.

Отдельное согласие не установлено заранее. На сервере проверяются актуальная версия, согласие, выбранный тип карты и USD. В priceSnapshotJson существующего booking сохраняются полный локализованный текст согласия, версия и время. Персональные данные рождения не передаются стороннему процессору; внешний карточный сервис в этом контуре вообще не вызывается.

Checkout имеет приватный адрес. Одобрение карты без поступления не подтверждает заказ. Mock settlement содержит отдельные идентификаторы сессии и перевода, ожидаемые net, получателя, сеть и токен. Только проверенный mock receipt переводит существующий заказ в confirmed. Redirect клиента ничего не подтверждает.

После подтверждения используется существующая очередь отчётов, расчёт/PDF, контроль качества и одобрение владельцем. Повторное подтверждение повторяет безопасную попытку постановки того же задания; данные платежа и заказа хранятся в MySQL. Фоновая сверка восстанавливает enqueue после сбоя. Приватная ссылка доступна до завершения подготовки, затем позволяет скачать утверждённый PDF; эта же ссылка включается в письмо. Принятие mock-письма сервисом не равно проверке доставляемости настоящей почты.

Не создавалась отдельная production-система заказов и не добавлялись миграции. Дополнительная служебная информация sandbox хранится в JSON-снимке существующего заказа. Для полноценного реального платёжного канала по-прежнему нужны отдельные payment attempts/settlement claims/outbox и реальные доказательства поступления по спецификации провайдера.

## Ручной возврат

Выполняет продавец, не RiskPay. Реальных кошельковых операций здесь нет.

1. Покупатель отправляет заявку из приватного checkout. Переход к нему есть и со страницы статуса заказа.
2. Авторизованный владелец открывает `/sandbox/card-owner`, выбирает заявку и основание возврата. Пользователь без доступа владельца не может рассчитать/подтвердить возврат.
3. Для добровольного допустимого возврата рассчитываются 20% **от исходной суммы возврата**, затем отдельно указанная комиссия сети. Комиссии RiskPay повторно не удерживаются. Например: 50 USDC − 10 USDC − 0,01 USDC = 39,99 USDC.
4. Для обязательного полного возврата предусмотрен отдельный вариант без удержаний с покупателя. Это исключение сохраняется и в тексте согласия; юридическая допустимость обязательного crypto-only возврата и удержаний не считается подтверждённой.
5. Покупатель видит точную разбивку, подтверждает её версию и свой ненулевой адрес Polygon. Без этого этапа даже владелец не может подтвердить перевод.
6. Принятие расчёта блокирует новые операции исполнения под блокировкой booking. При активной генерации или отправке письма требуется дождаться завершения/сверки.
7. Владелец запускает **тестовый** перевод и проверку. При принятии расчёта фиксируются неизменяемые сумма, получатель, quoteId, время и тестовый начальный блок. Офлайн RPC-фикстура проходит тот же verifier сети/USDC/суммы/адресов/финальности, что подготовлен для ручного перевода. После проверки под блокировкой заказа ещё раз сравнивается intent и атомарно закрепляется уникальный log claim. Только затем появляется refunded и reference с префиксом fixture. Повтор подтверждения не создаёт ещё один расход; чужой claim отклоняется. Повтор оплаченного callback не снимает блокировку возврата.

Синтетические claims возврата имеют отдельный префикс `fixture-refund:` и не могут
занять идентификаторы реальных blockchain-поступлений. Перевод на адрес продавца
вместо адреса покупателя отклоняется. Это по-прежнему проверка искусственных данных:
фикстура не вызывает реальный RPC и не отправляет криптовалюту.

В песочнице используется условный курс 1 USD = 1 USDC и тестовая оценка net settlement 83,5% от gross. Это не реальный курс и не гарантированный тариф RiskPay. Для реального возврата нужны срок действия котировки, актуальный источник курса, выбор конкретного контракта USDC, доказательство суммы/адреса/сети исходящего перевода и отдельное согласование владельцем. Нельзя помечать реальный возврат выполненным только по нажатию кнопки или вводу произвольного hash.

## Запуск на этом компьютере

Нужны Node, зависимости проекта, Docker/Colima и Google Chrome для проверок. Используются отдельные MySQL `vedic_card_sandbox`, S3 bucket `vedic-card-sandbox` и Docker volumes с префиксом `karma-card-sandbox`. Рабочие ключи не нужны.

Для новой установки скопировать `.env.card-sandbox.example` в `.env.card-sandbox`. Последний исключён из Git. В нём только синтетические локальные данные.

```sh
colima start --cpu 2 --memory 4 --disk 20
docker-compose -f deploy/compose.card-sandbox.yml up -d --build
node --import tsx scripts/card-sandbox-local.mjs storage
node --import tsx scripts/card-sandbox-local.mjs migrate
node --import tsx scripts/card-sandbox-local.mjs seed
pnpm build
node --import tsx scripts/card-sandbox-local.mjs start
```

Runner читает только `.env.card-sandbox`, проверяет sandbox deployment, локальный URL и sandbox-базу. Миграция/seed выполняются только для этого контура. Повторный seed удаляет его синтетические fixture-заказы; не запускать его для сохранения уже созданных тестовых сценариев.

- Сайт: http://127.0.0.1:3000/?lang=ru
- Вход тестового владельца: http://127.0.0.1:3000/api/auth/login?token=sandbox-login-token-change-me-32-characters
- Карточные заказы/возвраты владельца: http://127.0.0.1:3000/sandbox/card-owner?lang=ru
- Студия отчётов: http://127.0.0.1:3000/admin/report-studio
- Mock-письма: http://127.0.0.1:4010/messages

Тестовая ссылка входа годится только для loopback sandbox; это не production-учётная запись.

## Проверки

```sh
pnpm check
node --import tsx scripts/card-sandbox-local.mjs visual
node --import tsx scripts/card-sandbox-local.mjs test
```

`visual` проверяет четыре языка и мобильный overflow. `test` дополнительно создаёт настоящий sandbox booking через существующий API, проверяет отсутствие генерации после одного лишь card approval, подтверждает mock settlement, ожидает PDF, одобряет его тестовым владельцем, проверяет одно mock-письмо и приватную выдачу PDF, затем проходит ручной возврат. Также проверяется отправка формы сайта с Mastercard и отдельным согласием.

Текущая диагностика без создания заказа:
`node --import tsx scripts/check-card-sandbox-readiness.mjs`.
Она сохраняет несекретный результат в `artifacts/card-sandbox-readiness-2026-11-03.json`
и отдельно показывает готовность песочницы и отсутствие готовности live-платежей.

Резерв: весь net-остаток заказа удерживается 14 суток с первого подтверждённого
поступления. Открытый возврат/спор или неизвестная дата сохраняют удержание.
Владельцу показываются удерживаемая сумма, доступный к распределению остаток и дефицит;
это внутренний тестовый учёт, а не реальный баланс кошелька или автоматический перевод.

Публичный приёмник fixture-событий действует только до настроенного
`RISKPAY_CALLBACK_EXPIRES_AT` (ISO UTC, не более часа). После истечения срока новые
заказы автоматически используют локальный callback; старые тестовые адреса не
следует повторно использовать. При повторном развёртывании нужно обновить и URL,
и срок в `.env.card-sandbox`, затем перезапустить приложение. Основной сервер
и GitHub от этой операции не обновляются.

Снимки интерфейса сохраняются в `artifacts/card-sandbox-*.png`. Они локальные; не следует включать тестовые приватные ссылки в публичные материалы.

## Что остаётся до настоящих платежей

Подтвердить договорный маршрут, провайдера карты и возможности продавца из Панамы; получить реальную спецификацию сессий/подписей/settlement/refund; проверить адрес и контракт USDC; утвердить юридический текст и конкретные исключения для комиссий; внедрить реальную сверку поступлений/переводов и расширить DB-конкурентные проверки. Нажатия sandbox-кнопок не являются проверкой Visa/Mastercard или настоящих выплат RiskPay.

Публикация кода на GitHub, деплой сервера, регистрация платёжного аккаунта и реальные платежи в эту задачу не входят.

## Результат проверки 3 ноября 2026

- TypeScript: успешно.
- Сборка Vite и серверного bundle: успешно; предупреждения о размере существующих JS-чанков не блокируют сборку.
- 84 целевых unit/regression-теста: успешно (карточная модель, согласия, расчёт удержаний, границы sandbox, существующие booking/payment/crypto callbacks, возвраты и доставка).
- 6 браузерных проверок Chrome: успешно. В том числе полный цикл с MySQL/MinIO и mock-почтой, четыре языка на мобильном экране и отправка реальной формы сайта с выбором Mastercard.
- Полный цикл подтвердил единственное задание отчёта, одно письмо с PDF, проверенный приватный PDF download, запрет действий владельца для неавторизованного клиента, согласие на конкретную сумму возврата и сохранение refunded после повторного платёжного события.
- Отчёт перед отправкой одобрялся тестовым владельцем через существующий механизм качества. Автоматическое одобрение нового карточного канала не включалось.

Проверено именно локальное моделирование. Настоящие карты, реальные входящие USDC и исходящие ручные переводы не использовались.
