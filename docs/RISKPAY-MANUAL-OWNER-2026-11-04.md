# RiskPay: ручная проверка оплаты и отправки PDF

Решение владельца от 4 ноября заменяет прежнее требование полностью автоматической
карточной выдачи. Поступление USDC проверяется сервером, но не объявляется
доказательством полного карточного списания. Владелец явно принимает фактическую
сумму для конкретного заказа, затем отдельно проверяет и отправляет PDF.

## Рабочий процесс

Кабинет: `/owner/riskpay`, ссылка RiskPay в Control Room. Доступ только к
существующей авторизованной сессии владельца сайта. Страница и API не кэшируются.

1. Покупатель создаёт заказ. Фиксируются цена, продукт, язык, имя, email и данные
   рождения. Для заказа запрашивается отдельный адрес RiskPay и секрет callback.
   Apple Pay / Google Pay — предпочтение; доступность определяет hosted gateway
   по стране, устройству, сумме и провайдеру. Наличие кнопки не обещает доступность.
2. Callback лишь сохраняет кандидата. Независимый Polygon RPC проверяет native
   USDC, финальность/каноничность блоков, перевод на адрес этого заказа и перевод
   с него на кошелёк продавца. Проверяется точная фактическая сумма; вымышленной
   котировки и процента комиссии нет. Одна пара tx/log глобально принадлежит одному
   заказу через существующий уникальный индекс `verified_payment_claims`.
3. Заказ получает `received_review`, не `confirmed`. PDF не создаётся. Владелец
   видит покупателя, email, данные рождения, цену USD, оба адреса, обе транзакции,
   поступившие USDC, время поступления и уникальную привязку. Разница переводов не
   выдаётся за общую комиссию банковской карты. При потере callback владелец может
   указать оба tx hash и входящую сумму: они всё равно проверяются сервером.
4. Владелец повторяет номер заказа, подтверждает принятие фактической суммы и
   записывает основание. Решение атомарно фиксируется с actor/time/claim. Только
   после этого статус становится `confirmed`, создаётся единственное задание.
   После перезапуска worker восстанавливает очередь принятого заказа.
5. Готовый PDF остаётся `needs_review`. Владелец открывает именно эту версию,
   проверяет страницы, повторяет номер заказа и email получателя. Подтверждение
   связано с version ID, SHA-256 и адресатом. Затем используется существующая
   доставка с уникальным idempotency key и проверкой байтов PDF.
6. Результат показывает точный адресат, статус, ID почтового сервиса, время и
   попытки. `sent` означает принятие почтовым сервисом, не попадание во входящие.
   При сбое доступен повтор той же одобренной версии в пределах окна дедупликации;
   после 23 часов существующая защита требует ручной сверки журнала.

Изменение получателя, данных рождения, продукта или цены инвалидирует решение;
устаревшая вкладка не может подтвердить изменённый снимок. Изменение версии PDF
требует нового решения. Обычная bulk/legacy отправка для таких заказов запрещена;
Report Studio направляет владельца в связанную очередь RiskPay.

## Клиент и возвраты

Личная страница `/card-order/<capability>` показывает номер, сумму и этапы,
позволяет вернуться в gateway до проверенного поступления, открыть status/PDF и
запросить ручной возврат. Она не раскрывает email, адреса/секрет callback или ipn.
Запрос возврата ставит `refund_pending`, останавливает новую подготовку/отправку.
Он не отправляет криптовалюту и не объявляет возврат исполненным.

Существующая политика добровольного возврата 20% + раскрытая комиссия сети и
исключения обязательных прав сохраняются. Перевод возврата остаётся ручным.
Новый ledger учитывает поступления, но пока не автоматизирует сверку выполненных
вручную возвратов. Эти заказы остаются удержанными; интерфейс не показывает их
остаток как доступный для вывода. Резерв всего проверенного остатка — 14 суток
от первого поступления; непринятые/спорные заказы удерживаются дольше. Это учёт,
а не ограничение кошелька или окончание юридических обязательств.

## Production configuration

По умолчанию live выключен. Для этого отдельного ручного режима нужны:

```
RISKPAY_LIVE_ENABLED=true
RISKPAY_FULFILLMENT=owner_review
RISKPAY_MERCHANT_WALLET=<проверенный публичный Polygon адрес продавца>
RISKPAY_POLYGON_RPC_URL=<независимый HTTPS Polygon RPC>
```

Также обязательны штатные `DEPLOYMENT_MODE=independent`, публичный HTTPS
`PUBLIC_BASE_URL`, рабочие БД, R2, AI и Resend. Никаких новых private keys или
платных аккаунтов не требуется. Старый `cardSandbox` не превращается в live:
реальный ручной режим использует отдельный `riskpayManual` снимок.
Новых таблиц и миграций нет. Откат: выключить `RISKPAY_LIVE_ENABLED` для новых
заказов; сохранить существующие снимки и доступ к очереди владельца.

## Проверка

- 30 unit-проверок независимого receipt, фиксации адресата/данных/версии и gating.
- Полный unit suite: 595 passed, 20 skipped до финальных UI-уточнений.
- Браузерный сценарий `e2e/riskpay-manual.spec.ts`: только отдельная локальная
  песочница, синтетический receipt и локальный почтовый симулятор. Проверяются
  два явных решения, конкурентные нажатия, один job/email, точные байты PDF,
  запрет чужого email, устаревшей вкладки и пауза по запросу возврата.
- Финальный локальный браузерный прогон: 2 passed (57.7 s). Два отдельных
  подтверждения, один job/email при пяти одновременных запросах, SHA-256 PDF
  совпал; неверный email/версия и изменённый заказ отклонены.
- TypeScript и production build прошли. После финальных UI/guard изменений
  повторно прошли 53 целевых теста. Production-проверки ещё не выполнены.
  Реальных карточных списаний пока не было.

Поддержке RiskPay сообщения не отправляются по указанию владельца.
