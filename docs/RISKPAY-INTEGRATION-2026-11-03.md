## Что реализовано

Последняя доработка возврата: verifier подключён к **fixture-сценарию**, а не оставлен
отдельным модулем. Согласие фиксирует intent; офлайн доказательство проходит проверку
перевода; после этого intent повторно сравнивается под блокировкой и log claim
атомарно закрепляется за заказом. Синтетический namespace `fixture-refund:` исключает
смешивание с реальными claims. Результат содержит явный `fixture:` reference.
Тесты подтвердили запрет self-transfer, отказ при чужом claim и один расход при
восьми одновременных подтверждениях. Прогон: 44 целевых unit/regression и 3 браузерных
сценария прошли; TypeScript и серверная сборка прошли. Реальные переводы не выполнялись.

- Реальный API-клиент RiskPay по публичной документации: создание временного кошелька, безопасное построение hosted checkout URL, ручной запрос статуса по ipn_token.
- Существующая sandbox-форма подключена к этому клиенту через **офлайн transport**, который воспроизводит документированный ответ. Сетевых обращений к RiskPay не выполнялось. Это следующий этап после первоначальной чистой модели платежей, но не подтверждение live-интеграции.
- Apple Pay и Google Pay добавлены в выбор оплаты рядом с Visa/Mastercard и криптовалютой, с локализацией на четырёх языках и сохранением выбранного способа в заказе.
- Выбор Apple/Google — предпочтение. API не документирует параметр для принудительного открытия конкретного кошелька. Доступность определяется hosted checkout по провайдеру, устройству, региону, валюте и сумме. На сайте не имитируются настоящие кнопки Apple Pay SDK / Google Pay SDK, а показывается выбор способа с явной оговоркой о доступности.
- Callback соответствует документированной GET-схеме, содержит уникальную связь с заказом и проверяется по выделенному адресу. Он сохраняется как повод для сверки и **не подтверждает paid**. Платёжные симуляции запрещены для сессий, созданных в live-режиме.
- Добавлен независимый проверяющий модуль: точный контракт native USDC Polygon, финальность и канонический блок, входящий перевод на временный адрес и исходящий перевод продавцу, суммы по авторитетной котировке, уникальная идентичность transfer log. При отсутствии авторитетной котировки результат — under_review.

## Проверенные первичные источники

[RiskPay API](https://documenter.getpostman.com/view/2104539/2sB2cPkRGz) прочитан через браузер; текстовый web-инструмент содержимого не показывал. Установлены:

- `GET https://api.riskpay.biz/control/wallet.php`: `address`, уникальный `callback`; ответ содержит `address_in`, `polygon_address_in`, `callback_url`, `ipn_token`.
- Для общего выбора провайдера используется `https://pay.riskpay.biz/payment-creating.php`: зашифрованный адрес, email, amount, currency. Параметр выбора Apple Pay или Google Pay не описан.
- Callback — GET на исходный URL с `value_coin`, `coin`, `txid_in`, `txid_out`, `address_in`. Документация не описывает HMAC/подпись такого события. Наш приватный token в исходном callback URL — собственная привязка к заказу, не подпись RiskPay.
- `GET /control/payment-status.php` принимает `ipn_token`; документированы paid/unpaid. Сам RiskPay просит не использовать endpoint для частого автоматического опроса. В фоновом worker его опрос не добавлялся.
- `value_coin` описывает криптосумму, отправленную провайдером на временный адрес; нельзя автоматически считать её окончательной суммой продавцу или исходной стоимостью покупки в USD.

[Circle: USDC contract addresses](https://developers.circle.com/stablecoins/usdc-contract-addresses): native USDC в Polygon — `0x3c499c542cef5e3811e1192ce70d8cc03d5c3359`. Это не доказательство того, что RiskPay использует именно native USDC: документация допускает coin labels, но не закрепляет точный контракт. До live необходимо подтвердить этот актив; USDT0 и bridged USDC автоматически не принимаются вместо native USDC.

[RiskPay: технические ограничения](https://riskpay.biz/payment-gateway/): redirect на hosted checkout, iframe запрещён. Минимум оплаты зависит от провайдера. Например, низкая цена отдельного продукта сама по себе не доказывает наличие подходящего карточного маршрута.

## Что намеренно не включено

```env
RISKPAY_MODE=fixture
RISKPAY_LIVE_ENABLED=false
RISKPAY_MERCHANT_WALLET=
RISKPAY_CALLBACK_BASE_URL=
```

В примере callback пустой. В локальной `.env.card-sandbox` callback теперь указывает на отдельный HTTPS-приёмник `https://starlordkarma-riskpay-fixture.netlify.app`. Режим остаётся fixture, реальные платежи выключены, merchant wallet пустой. Адрес существующего криптокошелька не изменялся и в RiskPay не передавался. API-ключ или регистрация для описанного публичного API не требуются; запрашивать у владельца выдуманные ключи нельзя.

Код отдельного live-клиента подготовлен, но **внешний маршрут и автоматическое подтверждение настоящего платежа не проверены и не готовы к запуску**. Одного переключения флагов недостаточно для коммерческого использования.

После повторной проверки создание live checkout дополнительно запрещено в коде до реализации авторитетной котировки. Тестовые команды подготовки и подтверждения возврата для live-заказов отклоняются. Подробная схема получения денег, резервирования средств на возвраты и черновик вопросов поставщику: [RISKPAY-LIVE-ACCEPTANCE-2026-11-03.md](RISKPAY-LIVE-ACCEPTANCE-2026-11-03.md).

## Конкретные препятствия для live

1. Основной sandbox находится на loopback HTTP. Отдельный публичный TEST endpoint создан по разрешению владельца, но это не production-доставка: он закрывается через час, принимает только заранее зарегистрированные fixture-заказы и доставляется локальным подписанным pull-клиентом. Для live нужен постоянный HTTPS callback и постоянно работающая доставка/мониторинг.
2. Нужно подтвердить использование существующего адреса владельца именно для получения выбранного USDC Polygon и точный контракт актива RiskPay. Приватный ключ серверу не нужен.
3. Нужна документированная котировка/правило сопоставления gross заказа, входящего USDC и фактического net продавцу. Рекламные 12% + ориентировочная комиссия не заменяют котировку конкретного платежа. В live-модели иллюстративные 83,5% из старой песочницы не используются как доказательство оплаты.
4. Подключение независимого Polygon RPC и атомарных DB claims для transfer logs реализовано, но не выполнялось на настоящих поступлениях. RPC включается только при явной локальной настройке; без авторитетной котировки callback остаётся в review. Фоновая сверка повторяет проверку сохранённых транзакций через независимый RPC, не опрашивая RiskPay status API.
5. Коммерческая допустимость конкретного on-ramp для продавца из Панамы и цифровых прогнозов, No-KYC на всём маршруте и условия ручных возвратов остаются предметом договорного подтверждения.

До устранения этих пунктов нельзя объявлять, что сайт уже принимает настоящие Visa/Mastercard, Apple Pay или Google Pay и гарантированно выдаёт продукт по реальной оплате.
